# Mobile-first Quran reader SPA with offline support

A greenfield vanilla-JS single-page application implementing a Quran reader ("Muslim Pedia") with hash-based routing, five pages (home, surah detail, search, bookmarks, settings), audio playback with auto-advance, localStorage persistence, and a service worker for offline use. The app fetches all data from equran.id's public API and renders it with a mobile-first Islamic green aesthetic. Three IIFE modules (API, Storage, App) with clear separation.

**Watch for:** The ayah-text search fetches all 114 surahs sequentially over the network with no cancellation mechanism (confirmed). XSS vectors exist in innerHTML rendering of API-sourced content (likely). The service worker caches API responses indefinitely with no size limit or eviction strategy (confirmed).

## High-level view

The app uses a single HTML page with show/hide sections governed by `hashchange`—no build tools, no framework overhead—but all DOM is created upfront and page-specific JS runs unconditionally on load.

The API layer caches only the surah list in JS memory. Surah detail responses live solely in the service worker's cache storage, so navigating back to a previously viewed surah shows a skeleton flash even with a warm SW cache (network-first strategy means the skeleton appears until the fetch resolves or fails).

Audio playback holds a single `Audio` instance with auto-advance to the next ayah on end. There's no cleanup when navigating away from the surah detail page, so audio continues playing in the background if the user taps "Home" mid-playback.

The service worker caches all API responses indefinitely in a single cache bucket with no TTL or size eviction. For 114 individual surah-detail responses (each 10–200 KB), cache storage could grow substantially on constrained devices.

Search in "ayah" mode serially fetches every surah's detail from the API until it finds 20 matches or exhausts all 114 surahs. There's no debounce cancellation—if the user types another character, a second search starts without aborting the first, potentially resulting in interleaved DOM updates and redundant network traffic.

<details>
<summary>Issues (6)</summary>

1. **XSS via innerHTML with API data** — `teksArab`, `teksIndonesia`, `namaLatin`, and other API fields are interpolated directly into innerHTML templates without sanitization. If the API ever returns content with embedded HTML or script, it executes in the user's session. Escape HTML entities before insertion, or use `textContent` for text-only fields.
2. **Audio continues after navigation** — No code stops the `currentAudio` when the user navigates away from the surah-detail page. Call `currentAudio.pause()` in `showPage()` or on `hashchange` when leaving the detail view.
3. **Unbounded ayah search with no cancellation** — `searchAyahs` fetches up to 114 surah details sequentially. A new keystroke starts a parallel search without aborting the previous one. Use an AbortController per search invocation and cancel the prior one on each new input.
4. **Service worker cache grows without eviction** — Every unique API URL is cached forever in `CACHE_NAME`. Add a max-age check or limit cached entries (e.g., LRU eviction for surah-detail responses).
5. **Global retry via `window._retryFn`** — The error-state retry button writes a function to `window._retryFn`, which is overwritten if a second error renders before the first is clicked. Pass a unique identifier or use event delegation instead.
6. **`surahName` injection in bookmark onclick** — The `toggleBookmark` inline handler interpolates `surahName` as a string literal: `'${surah.namaLatin}'`. A surah name containing a single quote would break the handler. Use escaped values or data attributes.

## XSS surface in template rendering

Every `renderSurahList`, `renderAyahList`, `renderAyahSearchResults`, and `renderLastRead` call interpolates API response fields directly into innerHTML template literals:

```js
container.innerHTML = surahs.map(surah => `
  <div class="surah-card" onclick="App.navigate('#surah/${surah.nomor}')">
    ...
    <div class="surah-latin">${surah.namaLatin}</div>
    <div class="surah-arabic">${surah.nama}</div>
  </div>
`).join('');
```

Fields like `teksArab`, `teksIndonesia`, `namaLatin`, `arti`, and `deskripsi` come from equran.id with no HTML escaping. The application has no defense if the upstream response changes or if service-worker-cached responses are stale/poisoned. A utility like `escapeHtml()` applied to every interpolated string would close this. For purely textual fields, `textContent` assignment on created elements is safer.

**Confirmed** — the code path is clear in `app.js` where template literals are used with raw API data.

## Audio lifecycle across navigation

The `currentAudio` instance lives in module scope with no teardown on route change. If a user is playing Surah Al-Baqarah ayah 100 and taps the Home nav button, `showPage('home')` fires but audio keeps playing. The `ended` handler then calls `playAudio(surahNomor, 101)`—if `currentSurahData` still references Al-Baqarah, the next ayah plays with no visible UI to stop it, and the auto-advance scrolls a hidden page.

Fix: in `showPage`, if the target isn't `surahDetail`, pause and reset `currentAudio`.

**Confirmed** — `showPage` only toggles CSS classes; no audio cleanup path exists.

## Sequential ayah search without cancellation

```js
async function searchAyahs(q, container) {
  for (const surah of surahs) {
    if (results.length >= maxResults) break;
    const detail = await API.getSurahDetail(surah.nomor);
    // ...
  }
}
```

Each `getSurahDetail` call waits for the network. Typing "sabar" triggers a search that may fetch 20+ surahs before finding matches. If the user refines to "sabar dan" 500ms later, the debounce fires a second `searchAyahs` while the first is still looping. Both write to the same `#search-results` container, causing flicker and potentially showing stale results from the first search above the second.

An `AbortController` stored per search invocation and aborted on the next one would fix this. Alternatively, a generation counter checked before each DOM write would prevent stale updates.

**Confirmed** — no cancellation mechanism exists in `searchAyahs`.

## Service worker cache growth

```js
if (url.hostname === 'equran.id') {
  event.respondWith(
    fetch(request).then((response) => {
      const responseClone = response.clone();
      caches.open(CACHE_NAME).then((cache) => {
        cache.put(request, responseClone);
      });
      return response;
    }).catch(() => caches.match(request))
  );
}
```

114 surah-detail endpoints accumulate in cache storage with no eviction. On mobile devices with limited storage, this could trigger the browser's quota-exceeded flow, silently failing the `cache.put` without notification. A LRU-style eviction (keep only the 20 most recently accessed surahs cached) would bound growth.

**Confirmed** — no eviction or size limit in `sw.js`.

## Global `window._retryFn` collision

```js
function renderError(message, retryFn) {
  window._retryFn = retryFn;
  return `<button class="retry-btn" onclick="window._retryFn()">...`;
}
```

The second call to `renderError` overwrites the first's retry function. Currently only one error can display at a time due to page show/hide, but the pattern is fragile. A safer approach: store retry functions in a map keyed by a generated ID, or use event delegation with data attributes.

**Likely** — single-error-at-a-time constraint holds today but is implicit, not enforced.

## String injection in inline handlers

```js
onclick="App.toggleBookmark(${surah.nomor}, '${surah.namaLatin}', ${ayah.nomorAyat})"
```

`surah.namaLatin` is interpolated as a JS string literal inside an HTML attribute. A surah name containing a single quote would break the onclick syntactically. Using `data-*` attributes and event delegation eliminates this class of bug.

**Possible** — current equran.id data lacks apostrophes in `namaLatin`, but no defensive escaping exists.
